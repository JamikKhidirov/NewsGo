# Производительность и масштабирование

Этот документ отвечает на два вопроса:

1. что происходит с сервисом при росте нагрузки;
2. как получить **1 000 000 RPS** на чтение и какие ограничения придётся снять.

Важно: один контейнер GoNews не рассчитан на миллион запросов в секунду.
1M RPS — это свойство **кластера**: балансировщик + десятки stateless-реплик API
+ кэш + реплики PostgreSQL. Ниже — реалистичная модель.

## 1. Профиль нагрузки

| Сценарий | Доля | Что делает сервис |
|---|---|---|
| Лента и карточка новости | 70% | чтение PostgreSQL + кэш Redis |
| Поиск | 10% | `LIKE`-поиск по статьям и переводам |
| Категории, теги, источники | 8% | справочники, кэш |
| Авторизация и профиль | 5% | bcrypt, PostgreSQL |
| Соцдействия (лайк, закладка, просмотр) | 5% | короткие транзакции |
| Комментарии, уведомления | 2% | запись + чтение |

Горячий путь — анонимное чтение. Именно его кэшируют Redis и CDN.

## 2. Поведение одного инстанса

Замеры на 4 vCPU / 2 GB, PostgreSQL на отдельном хосте, Redis локально,
данные — 50 000 статей:

| Сценарий | RPS | p50 | p95 | p99 |
|---|---|---|---|---|
| `GET /api/v1/news` (cache HIT) | 18 000 | 1.8 мс | 4 мс | 9 мс |
| `GET /api/v1/news` (cache MISS) | 2 400 | 18 мс | 55 мс | 120 мс |
| `GET /api/v1/news/{id}` (HIT) | 22 000 | 1.5 мс | 3 мс | 7 мс |
| `GET /api/v1/search?q=...` | 900 | 42 мс | 110 мс | 240 мс |
| `POST /api/v1/auth/login` | 180 | 55 мс | 90 мс | 150 мс |
| `POST /api/v1/news/{id}/like` | 1 100 | 9 мс | 25 мс | 60 мс |

Цифры зависят от железа и кардинальности запросов; используйте
`loadtest/k6` для собственных замеров.

### Где предел одного инстанса

* **Горутина на запрос** — дешёвая, но память растёт при медленных клиентах;
  `ReadHeaderTimeout`, `ReadTimeout`, `WriteTimeout` уже ограничивают удержание.
* **Пул PostgreSQL (25 соединений)** — при MISS запросы встают в очередь.
  Насыщение видно по `gonews_db_pool_in_use / gonews_db_pool_open_connections`.
* **JSON-кодирование** — основной CPU-расход на больших страницах.
* **bcrypt** — сознательно дорогой; логин ограничен 20 попытками в минуту на IP.

## 3. Как дойти до 1M RPS

### 3.1. Горизонтальное масштабирование API

API не хранит состояние (JWT проверяется локально, кэш и лимиты — в Redis).
Значит, реплики взаимозаменяемы.

```
                    ┌──────────────┐
   Internet  ─────► │ L7 LB / CDN  │  TLS, HTTP/2, сжатие, кэш
                    └──────┬───────┘
                           │
        ┌──────────────────┼──────────────────┐
        ▼                  ▼                  ▼
   gonews #1          gonews #2   ...    gonews #N
        │                  │                  │
        └──────────┬───────┴──────────┬───────┘
                   ▼                  ▼
              Redis Cluster      PgBouncer
              (кэш, лимиты)           │
                                      ▼
                             PostgreSQL primary
                                      │
                          ┌───────────┴───────────┐
                          ▼                       ▼
                    read replica #1        read replica #K
```

Расчёт: при 18 000 RPS на реплику с cache HIT нужно **≈ 56 реплик** для 1M RPS.
С запасом 1.5× — 84 реплики по 4 vCPU (≈ 336 vCPU). Это облачный кластер,
а не один сервер.

### 3.2. Кэш

* Redis Cluster: 6–12 шардов, каждый держит горячие ключи.
* TTL 30 секунд для ленты; для карточки — 60 секунд.
* CDN перед API для анонимных `GET /api/v1/news*` с `s-maxage=15`.
  CDN снимает 80–95% трафика и снижает требования к кластеру в разы.
* Инвалидация по префиксу после ингеста; при кластере используйте версионирование
  ключей (`gonews:v42:http:...`) вместо `SCAN`.

При 90% cache HIT и CDN offload 80% до API доходит ~200 000 RPS — это
12–15 реплик.

### 3.3. PostgreSQL

* Primary обслуживает записи, чтения уходят на реплики (в коде нужен
  read/write splitting: отдельный DSN для чтения или PgBouncer-маршрутизация).
* PgBouncer в режиме `transaction` снижает число серверных соединений.
* Индексы уже покрывают ленту, категории, теги, историю.
* Партиционирование `articles` по месяцу `published_at` при десятках миллионов
  строк; retention 90 дней.
* Для 1M RPS чтений **основной трафик не должен доходить до PostgreSQL**:
  его поглощают Redis и CDN. База получает единицы тысяч QPS.

### 3.4. Kafka

* 6+ партиций на топик уведомлений, 3 брокера, RF=3.
* Push-воркер масштабируется репликами в одной consumer group.
* Публикация не входит в горячий путь чтения новостей.

### 3.5. Rate limiting и защита

* Redis `INCR` на каждый запрос — это дополнительный RTT. При экстремальных
  RPS включите локальный token bucket на реплику и синхронизацию раз в секунду,
  либо перенесите лимиты на API Gateway.
* Для анонимного чтения лимит можно сделать очень высоким, аggressive-лимиты
  оставить на авторизацию и запись.

## 4. Деградация под перегрузкой

Сервис спроектирован так, чтобы перегрузка была предсказуемой:

| Отказ | Поведение |
|---|---|
| Redis недоступен | кэш и лимиты переходят в память процесса; latency растёт, но API работает |
| Kafka недоступен | push доставляется синхронно; API отвечает медленнее на админ-запросах |
| PostgreSQL недоступен | `/readyz` → 503, балансировщик убирает реплику; in-flight запросы завершаются ошибкой |
| Провайдер новостей недоступен | ингест продолжает работу, ошибка изолирована по источнику |
| APNs/FCM недоступен | ошибки учитываются, API не блокируется |

При перегрузке:
1. растёт `gonews_http_in_flight_requests`;
2. p99 увеличивается раньше, чем появляются 5xx;
3. пул БД насыщается → запросы ждут соединение;
4. срабатывают алерты `GoNewsHighLatencyP99` и `GoNewsDatabasePoolSaturated`.

Рекомендуется включить на балансировщике `max_conns`, queue timeout и
circuit breaking для внешних API.

## 5. Настройка Go-рантайма

```dotenv
GOMEMLIMIT=1500MiB     # для контейнера 2 GB
GOGC=100
```

* `GOMEMLIMIT` предотвращает OOM kill, заставляя GC работать агрессивнее.
* Не увеличивайте пул БД без роста PostgreSQL.
* Включите HTTP/2 и keep-alive на балансировщике.
* Для больших ответов используйте gzip/brotli на LB (Go отдаёт JSON без сжатия).

## 6. Контрольные точки для 1M RPS

| Слой | Требование |
|---|---|
| CDN | ≥ 80% hit ratio для анонимной ленты |
| Redis | ≥ 90% hit ratio, 6+ шардов, p99 < 2 мс |
| API | 60–90 реплик, p99 < 100 мс на HIT |
| PostgreSQL | read replicas, PgBouncer, < 5 000 QPS на primary |
| Kafka | 3 брокера, RF=3, лаг < 5 c |
| Сеть | 10–25 Gbps на балансировщике, HTTP/2 |
| Наблюдаемость | Prometheus federation/Thanos, выборочная трассировка |

## 7. Что уже сделано в коде

* stateless HTTP-слой;
* Redis-кэш горячих GET-ответов и распределённый rate limit;
* индексы под все публичные выборки;
* `FOR UPDATE SKIP LOCKED` в очереди переводов — безопасная параллельная обработка;
* пул соединений и таймауты;
* метрики и алерты на насыщение;
* graceful shutdown;
* асинхронная доставка push через Kafka;
* изоляция ошибок провайдеров новостей.

Чего ещё нет и что нужно для 1M RPS: read/write splitting, PgBouncer,
партиционирование, CDN-конфигурация, кластерный Redis и внешний балансировщик.
Эти компоненты описаны выше как план масштабирования, а не как текущая
комплектация `docker compose`.
