# Нагрузочное тестирование

В репозитории есть готовые сценарии [k6](https://k6.io/) в каталоге `loadtest/k6`.
Они проверяют чтение ленты, карточки, поиск, авторизацию, социальные действия и
push через админский API, а также позволяют построить модель до 1M RPS.

```
loadtest/k6/
  smoke.js            1 VU, 30 c — быстрая проверка после деплоя
  read.js             чтение ленты и карточек (основной профиль)
  mixed.js            реалистичное сочетание чтения, поиска и записи
  stress.js           ступенчатый рост до предела инстанса
  spike.js            резкий всплеск (проверка деградации и восстановления)
  lib/common.js       общие хелперы, проверки, тренды
  run.ps1             запуск на Windows
  run.sh              запуск на Linux/macOS
```

## Требования

* `k6` 0.50+ (<https://k6.io/docs/get-started/installation/>).
* Запущенный GoNews. Для честных замеров поднимите стек:

```bash
docker compose up -d --build
curl -s localhost:8080/readyz | jq
```

* Для нагрузочных прогонов **поднимите rate limit**, иначе вы измеряете 429,
  а не сервис:

```bash
GONEWS_RATE_LIMIT_PER_MINUTE=1000000 docker compose up -d gonews
```

Или запускайте сценарии с заголовком `X-Admin-Token` там, где это применимо,
и тестируйте с разных IP (k6 в облаке).

## Быстрый старт

```bash
# smoke: 1 виртуальный пользователь, 30 секунд
k6 run loadtest/k6/smoke.js

# чтение: 50 VU, 3 минуты
BASE_URL=http://localhost:8080 k6 run loadtest/k6/read.js

# смешанный профиль с записью (нужны ADMIN_TOKEN и тестовый пользователь)
BASE_URL=http://localhost:8080 \
ADMIN_TOKEN=devadmin \
TEST_EMAIL=load@example.com \
TEST_PASSWORD=password123 \
k6 run loadtest/k6/mixed.js

# ступенчатый стресс до 400 VU
k6 run loadtest/k6/stress.js

# всплеск: 10 -> 500 VU за 20 секунд
k6 run loadtest/k6/spike.js
```

Windows PowerShell:

```powershell
.\loadtest\k6\run.ps1 read
```

## Переменные окружения сценариев

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `BASE_URL` | `http://localhost:8080` | адрес API |
| `LANG` | `ru` | язык выдачи |
| `ADMIN_TOKEN` | пусто | `X-Admin-Token` для admin-запросов |
| `TEST_EMAIL` | `loadtest@example.com` | пользователь для login |
| `TEST_PASSWORD` | `password123` | пароль |
| `ARTICLE_ID` | пусто | карточка для точечных проверок |
| `READ_VUS` | `50` | виртуальные пользователи чтения |
| `READ_DURATION` | `3m` | длительность чтения |
| `MIXED_VUS` | `30` | VU смешанного профиля |
| `STRESS_MAX_VUS` | `400` | пик ступенчатого теста |

## Пороговые значения (SLO)

Сценарии падают, если нарушены цели:

| Метрика | Порог | Комментарий |
|---|---|---|
| `http_req_failed` | < 1% | ошибки 5xx и сетевые |
| `http_req_duration` p95 | < 300 мс | все запросы |
| `http_req_duration` p99 | < 800 мс | все запросы |
| `news_list_duration` p95 | < 150 мс | `GET /api/v1/news` |
| `article_duration` p95 | < 120 мс | `GET /api/v1/news/{id}` |
| `search_duration` p95 | < 500 мс | `GET /api/v1/search` |
| `checks` | > 99% | корректность ответов |

Значения подобраны для одного инстанса 4 vCPU / 2 GB с Redis. На слабом ноутбуке
или без Redis пороги нужно ослабить через `-e` или отредактировать сценарий.

## Что именно проверяется

* Коды ответов: `200` для чтения, `201` для создания, `401` для неавторизованных
  защищённых запросов.
* Структура JSON: наличие `data`, для списков — `meta.page/limit/total`.
* Непустая лента (`data.length > 0`) — иначе ингест не выполнен.
* `X-Cache` присутствует при включённом Redis (`HIT`/`MISS`).
* Логин выдаёт `accessToken`; защищённые запросы с ним возвращают `200`.
* Лайк и закладка идемпотентны: повторный запрос не ломает счётчики.
* `/metrics` содержит `gonews_http_requests_total`.
* `/readyz` возвращает `status=ready`.

## Как читать результаты

```
checks.........................: 99.82% ✓ 14973      ✗ 27
http_req_duration..............: avg=12.4ms min=1.1ms med=8.2ms max=980ms p(95)=41ms p(99)=120ms
http_reqs......................: 15000  82.6/s
```

* `http_reqs` / длительность = фактический RPS.
* Смотрите `p(95)` и `p(99)`, среднее почти бесполезно.
* Если `http_req_failed` растёт вместе с `http_req_duration` — это насыщение,
  а не ошибка кода.
* После прогона откройте Grafana: RPS, p99, in-flight, пул PostgreSQL,
  cache hit ratio. Сверьте цифры k6 и Prometheus — они должны совпадать.

### Признаки деградации

| Наблюдение | Причина | Что делать |
|---|---|---|
| 429 | низкий rate limit | поднять `GONEWS_RATE_LIMIT_PER_MINUTE` |
| p99 растёт, 5xx нет | очередь на пуле БД / CPU | больше реплик, кэш, индексы |
| 5xx > 1% | таймауты БД или OOM | проверить `docker stats`, `GOMEMLIMIT` |
| cache hit < 50% | короткий TTL или уникальные query | увеличить TTL, нормализовать ключи |
| RPS падает после всплеска | нет keep-alive / мал `max_conns` | настроить LB, `ReadTimeout` |

## Модель до 1M RPS

Один инстанс не держит миллион запросов в секунду. Ниже — расчёт кластера.

1. Измерьте RPS одного инстанса на вашем железе (`read.js`, cache HIT).
   Пример: 18 000 RPS при p99 < 10 мс.
2. Добавьте запас 30–50%: планируйте 12 000 RPS на реплику.
3. `N = 1 000 000 / 12 000 ≈ 84` реплики.
4. CDN перед API снимает 80% анонимного трафика → до приложения доходит
   200 000 RPS → **17 реплик**.
5. Redis Cluster (6–12 шардов) держит горячие ключи; PostgreSQL получает
   только промахи и записи (единицы тысяч QPS).

Пошаговый план масштабирования и требования к каждому слою —
[docs/ru/PERFORMANCE.md](PERFORMANCE.md).

## Распределённая нагрузка

k6 умеет запускать генераторы в Kubernetes:

```bash
kubectl apply -f - <<'EOF'
apiVersion: k6.io/v1alpha1
kind: TestRun
metadata:
  name: gonews-read
spec:
  parallelism: 20
  script:
    configMap:
      name: gonews-k6-read
      file: read.js
EOF
```

20 подов × 50 VU дают 1000 виртуальных пользователей. Сеть и балансировщик
должны выдерживать суммарный трафик; следите за `X-Request-ID` и логами Loki.

## Ограничения методики

* k6 с одной машины упирается в CPU генератора раньше, чем в сервер —
  смотрите `k6` CPU и используйте несколько генераторов.
* Docker Desktop на Windows добавляет сетевой overhead; для точных цифр
  запускайте k6 в Linux или в кластере.
* Внешние новостные API и переводчики не входят в нагрузочный профиль:
  ингест работает по расписанию и изолирован.
* bcrypt в логине ограничивает RPS записи; это осознанное решение.
